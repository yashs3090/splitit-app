# Fix geometry and scale, never binarize

The pipeline that works best for SplitIt's receipt photos is short, and it is the same on all three engines up to one point. First fix geometry: crop to the receipt, correct perspective, make the image upright. Then fix scale, so characters land in each engine's preferred pixel range. From there the engines diverge. **Tesseract.js is the only one that should get pixel-level work**: flatten the lighting in greyscale, set `user_defined_dpi`, and try its built-in Sauvola thresholding. **Apple Vision and ML Kit should get no pixel filters at all**, because neither vendor documents a benefit and the evidence on neural recognizers points to neutral or harmful effects. **No engine should get an externally binarized image.** Tesseract's own LSTM recognizer reads the grey pixels you pass in, and its maintainers rejected feeding it binary crops ([tesseract PR #4111](https://github.com/tesseract-ocr/tesseract/pull/4111)). This matters because SplitIt's failures so far (a 263×450 thumbnail that read 0 of 9 prices, "57.71" read as "57.1", a lost price and a stray "4" on El Chalan) are scale and segmentation failures. Filters do not fix those, and better sizing and cropping do. The cheapest wins are pure TypeScript and Tesseract parameter changes for web, which can be measured today with the Node Tesseract harness. The biggest native win is the OS document scanner (VisionKit on iOS, ML Kit Document Scanner on Android). It needs a development build, but it runs entirely on device, so it fits ADR 0010. The only techniques that would need a backend are learned dewarping, super-resolution and shadow-removal networks, and none of them earns its cost yet.

## Character height in pixels decides accuracy, not DPI or megapixels

Each vendor's resolution guidance reduces to the height of a character in pixels, and the targets differ. **Google's ML Kit wants each character at least 16×16 px and says nothing above 24×24 px helps** ([ML Kit v2 Android](https://developers.google.com/ml-kit/vision/text-recognition/v2/android)). Tesseract's docs say only "at least 300 dpi" ([ImproveQuality](https://github.com/tesseract-ocr/tessdoc/blob/main/ImproveQuality.md)). The more useful figure is community evidence: a 2018 test on Tesseract 4 found error rates tracked capital-letter height rather than DPI and fell to about zero at **30–33 px capital height**. Letters that were too large brought their own errors, such as `i` read as `1` ([tesseract-ocr Google Group](https://groups.google.com/g/tesseract-ocr/c/Wdh_JJwnw94)). iDigBio relays a related rule of an x-height of 20 px or more ([iDigBio](https://www.idigbio.org/content/resolution-requirements)). Apple publishes no pixel target. Vision instead ignores text smaller than `minimumTextHeight`, which defaults to **1/32 of the image height**, and it downsizes the input to match that setting ([Apple: minimumTextHeight](https://developer.apple.com/tutorials/data/documentation/vision/vnrecognizetextrequest/minimumtextheight.md); [WWDC19 Session 234](https://developer.apple.com/videos/play/wwdc2019/234/)).

SplitIt's own measurements fit this picture well. The 263×450 thumbnail went from 0/9 to 9/9 prices once upscaled to 1600 px, because its capitals were far below the Tesseract range. The already sharp 866×1390 receipt got *worse* at 1600–2048 px, which is the "too large" side of the willus curve. The current rule (upscale only below a 1000 px long edge) encodes this correctly, but it uses image size as a proxy for text size. A long receipt shot whole at 2048 px can still have small characters. An 80 mm receipt fills the height of a 2048 px frame with roughly 40–70 lines, so capitals come out around 15–30 px. That is my arithmetic from the notes, not a measurement. The better rule is to scale to a measured text height. Tesseract.js already returns `rowAttributes.rowHeight` per line when `{ blocks: true }` is requested ([index.d.ts](https://github.com/naptha/tesseract.js/blob/master/src/index.d.ts)), so a first pass can measure the median row height. A second pass then runs only if capitals fall outside roughly 25–35 px. Upscaling the whole image mainly changes segmentation and thresholding. The LSTM rescales each line crop to its fixed input height anyway (reported as 36 px, with linear interpolation and unsharp masking ([arXiv 2105.04515](https://arxiv.org/abs/2105.04515))), so what upscaling buys is detail that survives into that crop.

The native side runs on different arithmetic. A receipt that fills the width of a 2048 px portrait frame is about 1500 px wide. Spread over 42–48 characters, that is about 31–36 px per character, well above ML Kit's 24 px ceiling, so **the 2048 px cap costs nothing on Android** and saves memory. For Vision, the cap is also harmless at the default `minimumTextHeight`. The threshold is relative to image height, so resizing does not change which lines are filtered out. The real risk on iOS is the threshold itself. Small receipt lines take up only about 1–2% of a whole-receipt photo's height, under the 3.1% default, and WWDC19 says text below the minimum "will be ignored". This is an inference. Apple does not document behaviour near the threshold, but it is the most plausible explanation if Vision drops fine print on long receipts. It also implies that SplitIt's upscale rule probably does nothing for Vision: upscaling preserves relative text height. The code comment in `lib/imageSize.ts` already flags that Vision with this setting is unchecked on a device.

## Geometry is the one step every engine and vendor endorses

Cropping and perspective correction are the only steps with consistent support across vendors and the literature. Tesseract's docs say line segmentation quality "reduces significantly if a page is too skewed". They also say to crop to the text with a border of about 10 px, because both a tight crop and a big background border cause errors ([ImproveQuality](https://github.com/tesseract-ocr/tessdoc/blob/main/ImproveQuality.md)). In a CTPN-based system on the SROIE receipt benchmark, extracting the receipt area as a pre-processing step improved accuracy ([arXiv 1905.12817](https://arxiv.org/abs/1905.12817)). Apple's own presenters recommend the Document Camera because it "already [does] perspective correction of these scans for you and it evenly lights also the image", and they recommend `regionOfInterest` "to get rid of the noise surrounding it" ([WWDC19 Session 234](https://developer.apple.com/videos/play/wwdc2019/234/)). Google's equivalent advice is "ensure that the text occupies as much of the image as possible" ([ML Kit v2 Android](https://developers.google.com/ml-kit/vision/text-recognition/v2/android)). Cropping does double duty here: it removes table clutter that can produce stray tokens like El Chalan's leading "4", and it raises the pixels per character for a fixed size cap. **Cropping before the 2048 px cap matters more than any filter choice.**

The engines differ in how much geometry they absorb on their own. Vision's accurate path handles "rotated text or perspectively misaligned text" with "much broader support" than the fast path ([WWDC19 Session 234](https://developer.apple.com/videos/play/wwdc2019/234/)). ML Kit's Latin model gained "all-orientation support" in 2022–23 and reports non-rectangular corner points "due to the possible perspective distortions" ([ML Kit release notes](https://developers.google.com/ml-kit/release-notes); [Text.Element](https://developers.google.com/android/reference/com/google/mlkit/vision/text/Text.Element)). Both therefore tolerate tilt, and the gain from deskewing is likely smaller for them than for Tesseract. Tesseract.js offers a free small-angle deskew: `rotateAuto` runs line finding, reads the gradient and re-sets the image rotated when the angle is ≥0.005 rad. It does not fix 90°/180° rotation or perspective ([worker-script/index.js](https://github.com/naptha/tesseract.js/blob/master/src/worker-script/index.js)). Learned dewarping roughly halves Tesseract CER on curved pages: DocTr's ablation went from 0.68 to 0.31 ([DocTr, arXiv 2110.12942](https://arxiv.org/abs/2110.12942)). But those models are PyTorch research code, and UVDoc's authors caution that OCR scores on these benchmarks are high-variance ([UVDoc, arXiv 2302.02887](https://arxiv.org/abs/2302.02887)). Using them in SplitIt would mean a server or a Core ML/TFLite conversion, so they stay out.

Orientation has a SplitIt-specific wrinkle. `expo-mlkit-ocr` 0.2.7's Vision path passes the UIImage orientation to Vision, but it denormalizes boxes with the raw `cgImage.width/height`. Apple's sample instead scales by the oriented `image.size` ([Apple: Recognizing Text in Images](https://developer.apple.com/tutorials/data/documentation/vision/recognizing-text-in-images.md)). For a portrait photo tagged `.right`, that would swap the x and y scales. **The bug is unverified, and SplitIt likely already sidesteps it.** `lib/prepareImage.native.ts` always re-renders through `expo-image-manipulator`, and the image picker is called with `exif: false`, so Vision should receive an upright `.up` JPEG. On Android the same re-encode matters for a different reason: `InputImage.fromFilePath` documents nothing about EXIF handling ([InputImage reference](https://developers.google.com/android/reference/com/google/mlkit/vision/common/InputImage)). Both assumptions hinge on device check D4. Log `imageOrientation` and the box ranges once on a real portrait photo.

### Each platform's document scanner does the geometry for free

On native, nobody needs to write edge detection. Android's ML Kit Document Scanner (GA since Sep 2025) provides auto-capture, edge detection, cropping, rotation, shadow removal and stain or finger removal. It runs on device, needs no camera permission and adds about 300 KB ([Document Scanner](https://developers.google.com/ml-kit/vision/doc-scanner); [Android](https://developers.google.com/ml-kit/vision/doc-scanner/android)). It requires Play services and at least 1.7 GB of RAM, so the image-picker path must stay as a fallback. iOS has `VNDocumentCameraViewController` (iOS 13+) and, for photos already taken, `VNDetectDocumentSegmentationRequest` (iOS 15+), which returns four corners for a `CIPerspectiveCorrection` warp ([VNDocumentCameraViewController](https://developer.apple.com/tutorials/data/documentation/visionkit/vndocumentcameraviewcontroller.md); [VNDetectDocumentSegmentationRequest](https://developer.apple.com/tutorials/data/documentation/vision/vndetectdocumentsegmentationrequest.md)). `react-native-document-scanner-plugin` 2.0.4 (MIT, 54 KB, Expo config plugin, TurboModule) wraps the ML Kit scanner on Android and, reportedly, VisionKit on iOS. It needs a development build ([README](https://github.com/websitebeaver/react-native-document-scanner-plugin); [build.gradle](https://github.com/websitebeaver/react-native-document-scanner-plugin/blob/master/android/build.gradle)). Its compatibility with SDK 57, and whether it lets you force ML Kit's crop-only `SCANNER_MODE_BASE`, are unverified. The second question matters, because neither vendor shows that the "enhance" filters help OCR.

The web has no OS scanner, and the automated alternative is expensive. Official opencv.js 4.13.0 is a **10.96 MB** single file ([docs.opencv.org](https://docs.opencv.org/4.13.0/opencv.js)), and `@techstark/opencv-js` is 13.3 MB ([jsDelivr](https://data.jsdelivr.com/v1/packages/npm/@techstark/opencv-js@5.0.0-release.1)). jscanify, which wraps opencv.js, works best on a flat, uniform background ([jscanify](https://github.com/puffinsoft/jscanify)), and white receipts on white tables are exactly where contour detection fails. On web, a manual crop rectangle in the UI is cheaper and more reliable than auto-detection. Tesseract.js's `rectangle` option can then OCR just that region ([worker-script/index.js](https://github.com/naptha/tesseract.js/blob/master/src/worker-script/index.js)).

## Tesseract needs greyscale help; the neural engines want to be left alone

Tesseract is the one engine whose internals justify pixel work, and its internals also say where to stop. It always binarizes internally, using global Otsu by default (`thresholding_method` 0), with Leptonica adaptive Otsu (1) and Sauvola (2) as options since 5.0 ([tesseractclass.cpp](https://github.com/tesseract-ocr/tesseract/blob/main/src/ccmain/tesseractclass.cpp); [thresholder.cpp](https://github.com/tesseract-ocr/tesseract/blob/main/src/ccmain/thresholder.cpp)). The binary image drives layout and line segmentation only. **The LSTM crops each line from the original grey or colour image via `BestPix()`** ([tesseractclass.h](https://github.com/tesseract-ocr/tesseract/blob/main/src/ccmain/tesseractclass.h); [linerec.cpp](https://github.com/tesseract-ocr/tesseract/blob/main/src/ccmain/linerec.cpp)). On binarized input, maintainer stweil found "mixed" results, adding that "it is intentional to use the LSTM with original images" ([PR #4111](https://github.com/tesseract-ocr/tesseract/pull/4111)). Outside Tesseract, a DFKI study found grey-level text lines gave 24% and 19% lower error than binarized ones for an LSTM recognizer ([DFKI](https://www-live.dfki.de/fileadmin/user_upload/import/9313_Binarization-free_OCR_for_historical_documents_using_LSTM_networks.pdf)). There is counter-evidence: one comparative study credits Otsu with large Tesseract gains ([academia.edu](https://www.academia.edu/120306799/Synergizing_Optical_Character_Recognition_A_Comparative_Analysis_and_Integration_of_Tesseract_Keras_Paddle_and_Azure_OCR)). Its dataset is unseen, and Tesseract already applies Otsu internally, so the effect cannot come from Otsu per se. The conclusion is that **binarization should be steered inside Tesseract, not done before it**: if you hand Tesseract a binary image, the LSTM sees binary pixels too.

That leaves two levers for Tesseract. The first is illumination. Global Otsu is "suboptimal, particularly if the page background is of uneven darkness" ([ImproveQuality](https://github.com/tesseract-ocr/tessdoc/blob/main/ImproveQuality.md)), which is the normal state of a phone photo with a hand shadow or curl. Reflectance estimation as a preprocessing step improved Tesseract CER by 26% in one study ([arXiv 2011.14447](https://arxiv.org/abs/2011.14447)). The cheap classic form is background division: divide greyscale by a large-kernel blur or morphological closing, then rescale to 0–255. It flattens shadows and thermal-paper yellowing while leaving the LSTM a clean grey image, and it needs a few hundred lines of typed-array code, not opencv.js. The second lever is the thresholding parameters. Every `thresholding_*` parameter is a normal variable in the Tesseract fork that tesseract.js-core 7 bundles, so `setParameters` can set it ([fork tesseractclass.cpp](https://github.com/Balearica/tesseract/blob/2a9c1c49c360462733c386d2a44fcd22c4e21411/src/ccmain/tesseractclass.cpp)). There is a trap, though: window sizes are multiplied by DPI. Browser JPEGs carry no credible DPI, so Tesseract falls back to 70 dpi ([baseapi.cpp](https://github.com/tesseract-ocr/tesseract/blob/main/src/api/baseapi.cpp)), and **the Sauvola window shrinks to about 23 px**, smaller than a character's stroke neighbourhood on a 2048 px photo. Trying Sauvola therefore means setting `user_defined_dpi` (around 300) together with `thresholding_method=2`, and checking the result with the `imageBinary` output, which returns Tesseract's internal binary image ([dump.js](https://github.com/naptha/tesseract.js/blob/master/src/worker-script/utils/dump.js)).

Everything else is risky enough to stay opt-in and measured. CLAHE can amplify paper texture and thermal mottling, and I found no measured evidence for or against it with Tesseract LSTM. Median filtering and aggressive denoising can erase decimal points and the gaps between dot-matrix dots, and unsharp masking creates halos, which matters all the more because the LSTM already unsharp-masks lines internally ([arXiv 2105.04515](https://arxiv.org/abs/2105.04515)). Morphology belongs only to the edge cases tessdoc names: erode for ink bleed, dilate for broken strokes ([ImproveQuality](https://github.com/tesseract-ocr/tessdoc/blob/main/ImproveQuality.md)). On a receipt that means a small closing for dot-matrix print, at the risk of filling the counters of 0, 6 and 8. "57.71" read as "57.1" is the textbook small-glyph loss. The likely causes are a character too few pixels tall, JPEG ringing (SplitIt re-encodes at quality 0.9), or segmentation slicing a digit off. `imageBinary` will show which. Two Tesseract settings deserve an A/B test. `preserve_interword_spaces=1` keeps the wide gap between an item name and its price ([tesseractclass.cpp](https://github.com/tesseract-ocr/tesseract/blob/main/src/ccmain/tesseractclass.cpp)). Disabling `load_system_dawg`/`load_freq_dawg` may help abbreviations like "CHKN" ([ImproveQuality](https://github.com/tesseract-ocr/tessdoc/blob/main/ImproveQuality.md)); these are init-only and must go in `createWorker`'s config ([worker-script/index.js](https://github.com/naptha/tesseract.js/blob/master/src/worker-script/index.js)). On page segmentation mode, local evidence overrides the blogs. Guides recommend PSM 4 for receipts ([PyImageSearch](https://pyimagesearch.com/2021/11/15/tesseract-page-segmentation-modes-psms-explained-how-to-improve-your-ocr-accuracy/)), but on SplitIt's test receipt PSM 3 and 4 dropped the entire right-aligned price column (`docs/lessons/log.md`, M1a). **Keep PSM 6**, and retest 4 only after cropping, since uncropped background can confuse column detection.

Apple Vision and ML Kit get the opposite treatment. Apple documents no internal binarization or deskew step, and Google documents no internal preprocessing at all. Both name geometric and capture-side levers (focus, framing, resolution, a recapture prompt) rather than filters ([WWDC19 Session 234](https://developer.apple.com/videos/play/wwdc2019/234/); [Firebase ML Kit v1](https://firebase.google.com/docs/ml-kit/android/recognize-text)). The neural-OCR evidence that does exist leans neutral to negative. Greyscale slightly lowered EasyOCR accuracy on license plates, from 71.7% to 70.75% ([arXiv 2410.13622](https://arxiv.org/pdf/2410.13622)). Otsu matched no preprocessing on video text, where the authors argue CRNN convolution layers "essentially replace" preprocessing ([arXiv 1804.10687](https://arxiv.org/abs/1804.10687)). In an ID-document study, the best result came from PaddleOCR with no external binarization ([ResearchGate](https://www.researchgate.net/publication/355885450)). No study measures preprocessing on Vision or ML Kit specifically, so this rests on inference from similar engines. It is still enough to make "no filters" the default and put the burden of proof on any filter. The one exception is mild shadow evening of the kind `CIDocumentEnhancer` or the scanner's built-in cleanup provides ([CIDocumentEnhancer](https://developer.apple.com/tutorials/data/documentation/coreimage/cidocumentenhancer.md)), and even that should run as an A/B test.

### Per-engine pipeline at a glance

| Stage | Tesseract.js 7 (web) | Apple Vision (iOS) | ML Kit v2 (Android) |
|---|---|---|---|
| Crop / border | Manual crop rectangle or `rectangle` option; keep ~10 px margin | VisionKit document camera, or segmentation + `CIPerspectiveCorrection`; or `regionOfInterest` | ML Kit Document Scanner (prefer BASE mode); picker fallback |
| Orientation | Canvas draw applies EXIF (current) | Upright re-encode (current); verify D4 | Upright re-encode (current); `fromFilePath` EXIF undocumented |
| Deskew | `rotateAuto: true` | Not needed (accurate path tolerates tilt) | Not needed (all-orientation Latin) |
| Resolution | Scale to ~25–35 px capitals, measured from `rowHeight` | Keep ≤2048 cap; lower `minimumTextHeight` (needs native module) | 16–24 px/char; 2048 cap is fine |
| Colour / illumination | Greyscale + background division; CLAHE only if measured | None by default; optional `CIDocumentEnhancer` A/B | None by default; scanner cleanup A/B |
| Noise / morphology | None by default; small closing only for dot-matrix, measured | None | None |
| Binarization | None external; try `thresholding_method=2` + `user_defined_dpi=300` | None | None |
| Engine settings | PSM 6; test `preserve_interword_spaces`, dawgs off | Pin revision 3, `en-US`, `customWords`, `topCandidates(n)` | Expose confidence, angle and corner points |

## SplitIt's real limit is the thin native wrapper, not the pixels

Several of the most valuable native levers cannot be reached through `expo-mlkit-ocr` 0.2.7. On iOS its only method is `recognizeText(uri)`, with no options and `topCandidates(1)` only. On Android it calls `fromFilePath` with default options and passes JavaScript only the text and axis-aligned boxes, dropping ML Kit's per-element confidence, angle and corner points ([Text.Element](https://developers.google.com/android/reference/com/google/mlkit/vision/text/Text.Element)). The package has a single maintainer and about 136 weekly downloads ([Socket.dev](https://socket.dev/npm/package/expo-mlkit-ocr)). A small local Expo Module, or a fork, would unlock a set of settings Apple itself recommends. It could lower `minimumTextHeight`, the likeliest fix for fine print on long receipts. It could pin `VNRecognizeTextRequestRevision3`; Apple warns that "if you otherwise don't specify a revision, you will always get the latest and that might appear with some surprises" ([WWDC19 Session 234](https://developer.apple.com/videos/play/wwdc2019/234/)), and an unpinned revision would silently invalidate SplitIt's eval fixtures after an iOS update. It could set `recognitionLanguages=["en-US"]` and `customWords` such as SUBTOTAL and GRATUITY (custom words only work with language correction on), and read `topCandidates(n)` for price-shaped lines ([Recognizing Text in Images](https://developer.apple.com/tutorials/data/documentation/vision/recognizing-text-in-images.md)). It could also expose ML Kit's confidence for a "retake photo" prompt. Further out, iOS 26's `RecognizeDocumentsRequest` names receipts as a use case and groups table cells into rows ([RecognizeDocumentsRequest](https://developer.apple.com/tutorials/data/documentation/vision/recognizedocumentsrequest.md); [WWDC25 Session 272](https://developer.apple.com/videos/play/wwdc2025/272/)). It would have to sit behind an `#available` check above SplitIt's 16.4 floor.

Language correction is a judgment call to settle with fixtures. Apple's presenters turned it off for codes because "C001 ... can very easily be misconstructed as cool", then fixed S→5 and L→1 confusions in their own code ([WWDC19 Session 234](https://developer.apple.com/videos/play/wwdc2019/234/)). Receipt item names benefit from correction, and no source shows it rewriting prices. Keep it on, and run a correction-off pass only if the eval shows price damage. Under the user's rule, OCR misreads go to the totals banner rather than being patched in the parser.

On-device pixel libraries rank well below the scanner. `react-native-fast-opencv` 1.0.1 offers the full classic toolkit through JSI, but it is New Architecture only, links different OpenCV versions on iOS (4.9.0) and Android (4.12.0), and lists no CLAHE ([installation](https://github.com/lukaszkurantdev/react-native-fast-opencv/blob/main/docs/content/installation.md); [functions](https://github.com/lukaszkurantdev/react-native-fast-opencv/blob/main/docs/content/availablefunctions.md)). `@shopify/react-native-skia` 2.14 can express greyscale and contrast as a ColorMatrix, but it pulls in Reanimated 4 and worklets as peers ([npm](https://registry.npmjs.org/@shopify/react-native-skia); [color filters](https://shopify.github.io/react-native-skia/docs/color-filters)). `expo-image-manipulator` stays the geometry-only workhorse it already is ([Expo docs](https://docs.expo.dev/versions/latest/sdk/imagemanipulator/)). Since the evidence says the native recognizers do not want filters, neither pixel library is worth adding until a measured failure demands one.

### Experiment plan

Every recommendation above except "do not binarize externally" needs a measured result on SplitIt's own receipts. The published evidence is too generic, and the per-image filter-selection result in [Symmetry 2020](https://www.mdpi.com/2073-8994/12/5/715) suggests no single fixed filter wins everywhere. Measurement runs in two layers. The **Node Tesseract harness** (the one used for the upscale sweep) runs tesseract.js 7 with the production `TESSERACT_PARAMS` from `lib/webOcrEngine.ts` over the photos in the gitignored `receipts/` folder. It should write each variant's output as `eval/receipts/<name>.<variant>.ocr.json` in the shape the app saves. The **receipt-eval skill** then scores each variant with `npx tsx scripts/eval-receipts.ts`, reporting line-item accuracy (name roughly equal, cents exact), totals reconciled, and the three worst receipts. That script does not exist yet; the skill says to offer a build-task for it, and it is the first prerequisite. Each receipt also needs an `expected.json` in cents. Grow the set past the current three (El Chalan, La Cabaña, Raintree, plus Good Guy and the quantity case already on disk) to at least 15–20 receipts. Include long receipts, faded thermal prints, shadows and angled shots, because UVDoc's warning about high-variance OCR scores applies with full force to a set of three.

| Run | Variants (one factor at a time vs current baseline) | Tool | Decision rule |
|---|---|---|---|
| E1 Thresholding | `thresholding_method` 0/1/2 × `user_defined_dpi` unset/300 | Node harness → receipt-eval | Adopt if item accuracy rises with no receipt regressing by more than 1 item |
| E2 Scale | Current rule vs capital-height target 20/25/30/35 px (from first-pass `rowHeight`) | Node harness | Pick the flattest optimum; confirm the 866×1390 receipt does not degrade |
| E3 Illumination | None vs background division (kernel ≈ 3–5× line height) vs + CLAHE clip 2 | Node harness on `lib/preprocess.ts` output | Keep only steps with a net gain; CLAHE must beat division alone |
| E4 Engine knobs | `rotateAuto`, `preserve_interword_spaces`, dawgs off, PSM 4 after crop | Node harness | Same rule as E1 |
| E5 Crop | Full photo vs hand-cropped (10 px margin) | Node harness | Quantifies the value of a web crop UI |
| E6 Native capture | Raw picker vs scanner BASE vs scanner FULL/enhanced, same receipts | Dev build on iPhone and Android; save `.ocr.json`; receipt-eval | Scanner becomes default if ≥ raw on every receipt |
| E7 Vision knobs | `minimumTextHeight` 1/32 vs 0.015 vs 0.01; correction on/off | Dev build with #8; receipt-eval | Lower threshold if fine-print lines appear with no new junk |

Log each run's result in `docs/lessons/log.md` under `[area: receipt-parsing]`, and record the adopted pipeline as an ADR in `docs/learning/decisions/`. If line-item accuracy stays under 85% after E1–E7, ADR 0010 hands the decision about a Claude Edge Function fallback back to the user.

## Conclusion

The research changes the question. "Which filter makes OCR better" turns out to be the wrong framing, because for two of SplitIt's three engines the honest answer is none. The work that pays is upstream (framing, cropping, scale) and inside the engine (Tesseract's DPI and thresholding knobs, Vision's `minimumTextHeight` and revision). SplitIt's own upscale experiment already reproduced the literature's central finding: character height has an optimum on both sides, and fixed image-size rules only approximate it. Sizing to measured text height is the natural next step.

The less obvious implication concerns where engineering effort goes. The binding constraint on native accuracy is a thin, single-maintainer wrapper that hides the options Apple and Google expose, not missing CV code. A small owned native module (scanner plus recognizer options) is therefore worth more than any pixel library. It fits ADR 0010 entirely, because every technique that clearly needs a server (learned dewarping, super-resolution, neural shadow removal) addresses problems the platform scanners already solve well enough on device.
