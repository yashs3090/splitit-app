## Goal
The host can say who actually paid the restaurant, straight from the bill (including right after scanning): one person, or several people with amounts ("I paid $60, Sam paid $40.21"). Settle up then tells each person exactly whom to pay and how much, to the cent, with one Venmo link per payment.

## Design

### D1. Shared contract W: who paid (defined once; Tasks 1, 4b, 5, 6 point here)

**Storage.**
- `bills.payer_id`:
  - stays `not null` and always a participant (invariant P, unchanged);
  - in one-person mode, it's the person who paid;
  - in split mode, it's the **lead** (below).
- New `public.bill_payers (bill_id uuid, user_id uuid, paid_cents integer, primary key (bill_id, user_id))`:
  - `paid_cents` has `check (paid_cents between 1 and 99999999)`;
  - foreign key `(bill_id, user_id) → bill_participants (bill_id, user_id)`, `deferrable initially deferred`, no cascade (the same mechanism as invariant P; the deletion trigger cleans up, D8).

**Mode.**
- **One person** ⇔ the bill has **no** `bill_payers` rows. `payer_id` paid the whole bill. Its amount is **never stored**: it's always the current `bills.total_cents`, so it can never go stale (WP-10).
- **Split** ⇔ the bill has **2 or more** rows. Exactly one row is never valid: `set_payers` refuses it, the deletion trigger never leaves it, and pgTAP checks both.

**Lead.**
- The split row with the largest `paid_cents`. A tie goes to the lower `user_id`.
- Computed **only in the DB** (`set_payers` writes it to `bills.payer_id`). lib never computes it; it reads `payerId` (WP-21).
- uuid order in Postgres is byte order, which equals the order of the lowercase canonical text, i.e. JS string `<` on the ids. A shared tie fixture checks both sides (criterion 9).

**Valid split** (checked by `set_payers` on write, and by lib before calling):
- at least 2 entries, distinct `user_id`s, each a participant;
- each `paid_cents` an integer 1..99,999,999;
- **Σ paid_cents = bills.total_cents exactly**: tolerance **0**, sums in bigint / `Number.isSafeInteger` (WP-11).

**Stale** (split mode only): Σ paid_cents ≠ the current `bills.total_cents`. This happens when the host edits the total after setting amounts (`update_bill` doesn't touch `bill_payers`). While stale:
- `mark_paid` and `settle_difference` refuse with `22023 payers_stale`;
- lib's plan is `blocked_payers` (D4);
- the bill line asks the host to fix it (D6).

`gapCents = total − Σ paid`: positive means "left to assign", negative means "more than the total".

**Boundary table W.** Both sides test exactly these cases. pgTAP calls `set_payers`; Jest calls `validateSplit`. The live check runs both (criterion 34). Total = 10021 throughout.

### D2. Shared contract K: which marks a change of payers clears (Tasks 1, 4b, 7)

Let S′ be the new set of payers: `{p}` for one person, the entries' users for a split.

- **Cleared** = every row in `bill_marks` with `settled_at is not null` and `to_user ∉ S′`.
- Rows holding only a not-received flag aren't counted. They stay as 92 defined them (shown only while their recipient is a current payer).
- **Kept:** marks to anyone still a payer, **even if amounts changed**. Contract T then shows any difference on that pair (D4).
- `set_payer` (one person) and `set_payers` (split) both use K and the same `p_expected_cleared` token.
- **Regression:** a one-person → one-person change clears exactly today's set, because every mark was to the old payer.
- lib: `marksClearedBy(marks, newPayerIds): number`, in `lib/payers.ts`.

**Boundary table K** (both sides). Marks: Sam→A, Dee→A, Pat→B; Ann has a flag only, to A.

| # | Change | Cleared |
|---|---|---|
| K1 | one person A → one person B | 2 (Sam, Dee) |
| K2 | split A+B → split A+B, new amounts | 0 (event still logged) |
| K3 | split A+B → split A+C | 1 (Pat) |
| K4 | split A+B → one person A | 1 (Pat) |
| K5 | the identical split again | no-op (step 6), nothing logged |

### D4. Shared contract T: who pays whom (Task 2, pure; used by Task 6)

**Input:**
- a complete, non-all-zero bill's shares `s_u` (from `computeShares`, Σ = total);
- the payers `W = [(u, paid_u)]` (contract W; one person = `[(payerId, total)]`);
- `leadId` (= `bills.payer_id`);
- the pair marks `M` (from, to, cents, at, …).

**Output:** `transfers: Transfer[]`, where `Transfer = { fromId, toId, cents, kind: 'pay' | 'outside', mark, difference }`. `cents ≥ 0`; it is 0 only on a `pay` pair kept because it holds a mark.

**Algorithm (all integer cents; ids compared with JS `<` on lowercase uuids):**
1. P = payers; N = participants not in P.
2. **Assign each non-payer exactly one payer `a(i)`**, in this order:
   - a. **Sticky:** i has a mark to someone in P → `a(i)` = that payer. With several, the earliest `settled_at` wins, ties to the lower `to_user`.
   - b. `s_i ≤ 0` → `a(i)` = the lead.
   - c. The rest, by `s_i` descending, then id ascending. Each goes to the payer with the largest remaining capacity, ties to the lower id. Capacity `cap_p = paid_p − s_p − Σ s_j over j already assigned to p` (a and b count first).
3. Non-payer transfers:
   - `s_i > 0` → `pay` i → `a(i)`, `s_i`;
   - `s_i < 0` → `outside` `a(i)` → i, `|s_i|` (today's `payer_owes_them`: "settle that outside the app");
   - `s_i = 0` → none.
4. Payer residuals `r_p = paid_p − s_p − Σ_{a(i)=p} s_i`. Σ r_p = 0 always; assert it, and throw `RangeError` if not.
5. Payers settle among themselves greedily. Repeat until every r is 0: debtor d = the smallest r (ties lower id), creditor c = the largest r (ties lower id), `x = min(−r_d, r_c)`, add `pay` d → c `x`, then `r_d += x`, `r_c −= x`.
6. **Marks on pairs:**
   - every `pay` transfer carries its pair's mark;
   - a marked pair with no transfer appears as `pay` with `cents 0`;
   - `difference = differenceFor(cents, mark.cents)` (contract D, `SETTLE_DIFF_IGNORE_CENTS`, unchanged; a 0 target means "back").
7. Order: `pay` before `outside`; then by `fromId`, then `toId`.

**Properties** (property-tested; criterion 26):
- For every person u: `paid_u − s_u = Σ cents received − Σ cents sent`, counting every planned transfer (pay and outside, not the 0-cent kept pairs). So the result sums to zero.
- Every `pay` transfer goes **to a payer**.
- A non-payer has at most one transfer.
- At most `|participants| − 1` transfers with `cents > 0`.
- The same output for any input order of participants, payers or marks.
- **One payer = today, exactly.** With `W = [(payer, total)]`:
  - every non-payer is assigned to the payer;
  - `r_payer = total − s_payer − Σ others = 0`, so there are no payer-to-payer transfers;
  - the transfers are i → payer `s_i` (owes), payer → i `|s_i|` (outside), which is today's `settlePlan` (WP-5).

- One radio row per participant: the viewer first, then join order. The current payer is checked.
- **Tapping a name saves at once** (WP-13). The row shows a spinner, and every row is disabled meanwhile. It uses `pickerDecision`, generalised to contract K:

**Split the paying:**
- Fewer than 2 participants: the segment's body shows `Split the paying needs at least 2 people on the bill.` plus `Add people`. No fields.
- Bill total under 2¢: `Split the paying needs a total of at least $0.02.` No fields.
- Otherwise there's one row per participant (same order). Each row has the name and an amount field:

  - placeholder `0.00`, decimal keyboard;
  - hint `Leave blank if they didn't pay`.
- **Prefill:**
  - from split mode, the stored amounts (exact reload, WP-14);
  - from one-person mode, every field blank.
- **Running status line** (contract A, below), live-announced politely (see a11y).
- **`Add the rest`:** when the gap is > 0 and the focused field is blank or valid, a ghost button `Add the rest ($40.21)` appears under the focused row. It sets that field to (its value + gap).
- **Save** (primary) is enabled only when contract A says `canSave`. It sits under the status line. With marks present and K = 0, a muted note above Save: `Sam and Dee already paid. They may see a difference to settle.`
- **Confirm when K > 0** (inline, above Save): `Saving clears 2 payments already marked (Sam, Dee). They'll need to mark them again.` [`Save and clear`, danger] [`Cancel`].

**Contract A (`splitDraftStatus(fields, totalCents)`, `lib/payers.ts`):**
- Each field: trimmed `''` or a value that parses to 0 means **not paying**. Otherwise `parseMoneyInput` must give an integer 1..99,999,999, or the field is **invalid** (`Enter an amount like 12.50`; over the limit: `That amount is too large`).
- An invalid field **never** counts as $0 and never "adds up" (lesson 2026-11-21).
- `gap = total − Σ valid amounts` (safe integers).
- Status, first match wins:

| Status | Shown text | canSave |
|---|---|---|
| any field invalid | `Fix the amounts marked above` | no |
| fewer than 2 people with an amount | `Enter amounts for at least 2 people` (+ the gap line below it if gap ≠ 0) | no |
| gap > 0 | `$40.21 left to assign` | no |
| gap < 0 | `$3.00 more than the total` | no |
| gap = 0 | `Adds up to $100.21` (success tone, check icon) | **yes** |

- Boundary cases (Jest): Σ = total → yes; 1¢ under → `$0.01 left to assign`; 1¢ over → `$0.01 more than the total`; `0` and `''` → not paying; `abc`, `12.345`, `-5` → invalid; `999999.99` ok; `1000000.00` too large; two valid fields plus one invalid that would make it add up → no.
- `toPayersPayload(fields)` returns `[{ user_id, paid_cents }]`, people with an amount only, in participant order. That's what's stored and reloaded exactly.

## A1.2 The ledger model (replaces D2, D3 and D4; Tasks 1, 2, 4, 6)

### Plan key: how routes stay stable (WP-27)
Routes must change when the bill changes and must not change when someone pays.

**Approach:** each recorded payment stores the **plan key**, a fingerprint of the money-relevant bill state the payer's screen used when they paid. When working out routes:
- payments made under **another** key (or with no key) are history. They're folded into the positions, so routes are recomputed around them;
- payments made under the **current** key were made along today's routes. They only reduce the route they're on.

So recording a payment changes nothing else, and any bill change (a new key) recomputes everything from the positions, which gives the fewest payments overall.

```
planKey({ mode, leadId, payers, shares }) → 16 lowercase hex characters
canonical string: "v1|" + mode + "|" + leadId + "|" + payers sorted by userId as "id:paid" joined by "," +
                  "|" + participants sorted by userId as "id:share" joined by ","
hash: two 32-bit FNV-1a passes over the UTF-16 code units (offset bases 0x811c9dc5 and 0x01000193 XOR 0x9e3779b9), each as 8 hex
```
- `shares` are `computeShares` totals: the ready shares, or early "so far" shares (single payer only, A1.2 contract T step 0).
- The hash is a starting choice. The implementer may use any pure, deterministic 64-bit hash with evidence. The DB only checks the format (`^[0-9a-f]{16}$` or null).
- An item rename or any other change that doesn't touch money keeps the key, so it doesn't re-route anyone.

**Why not the alternatives (WP-27):**
- A server-side bill revision would need triggers on `claims`, `line_items`, `bills` and `bill_payers` that update one row per bill on every claim tap. That adds lock contention and interacts with Groups' claim triggers.
- The Activity log isn't a complete record of edits: a discount's `applies_to` change writes no event (lesson 2026-11-24).
- A persisted plan would have to be written by the client, because the DB can't compute shares (ADR 0021 §3).
- The cost of the key: it's client-supplied (honor system). A wrong key can only make routes recompute; money stays exact, because positions always use every payment.

### Contract P: the state of a pair (Task 2a; same rule in SQL, Task 4a-2)
For an ordered pair (u, v), take the entries between u and v, ordered by (`recorded_at`, `id`).
- The running net `r` counts u→v as +, v→u as −. `net = r` after the last entry.
- If `net > 0`:
  - `markAt` = the `recorded_at` of the entry that **started the latest positive run** (the last k where r(k−1) ≤ 0 and r(k) > 0);
  - `method` = the shared method of the u→v entries from k on, or `'other'` if they differ (SV-4 generalised).
- If `net ≤ 0`, u→v has no mark. (v→u may have one.)

A pair's 92-style **mark** is `{ cents: net, at: markAt, method }`. It's what the screens show and what the tokens carry: `settle_difference`'s `p_expected_cents`, and `mark_not_received`'s `p_expected_cents` / `p_expected_at`.

`recorded_at` is set from `clock_timestamp()`, not `now()`, so entries written in one transaction are ordered (lesson 2026-11-24). Ties are broken by `id`, so lib and SQL agree. Compare timestamps as the microsecond strings the API returns, not with `Date.parse` (nit N7).

### Contract T (ledger): who pays whom (Task 2b; lib only, because the DB can't compute shares)
**Inputs:**
- the shares `s`, Σ = total;
- the payers `W` (contract W; one person = `[(payerId, total)]`);
- `leadId`;
- the entries `E` (id, from, to, cents, method, planKey, at);
- the current key `K`.

**Steps:**

0. **Early single-payer plans only:** the unclaimed amount counts as the lead's share for routing, so positions sum to 0 (WP-39). Split bills never settle early (rule E′).
1. `pre` = entries with `planKey ≠ K` or null; `post` = entries with `planKey = K`.
2. Positions `p_u = paid_u − s_u + Σ pre sent by u − Σ pre received by u`. Σ p = 0; assert it, and throw `RangeError` otherwise. Planning a transfer u→v of x means `p_u += x`, `p_v −= x`.
3. **Pin negative shares (WP-30):** each **non-payer** with `s_i < 0` gets an `outside` route lead → i of `|s_i|` (today's `payer_owes_them`, settled outside the app). Apply it to p.
4. **Refunds (WP-29):** for each non-payer u with `p_u > 0` (by id), repay them from the people they paid. For each v by id with `net_pre(u→v) > 0`: plan v → u, `y = min(p_u, net_pre(u→v))`. This always brings u to 0: for a share ≥ 0, `p_u ≤` the net sent.
5. **Fewest transfers (WP-28)**, the same greedy as Groups GR-3: repeat while some p ≠ 0:
   - debtor d = the smallest p (ties to the lower id);
   - creditor c = the largest p (ties to the lower id);
   - plan d → c `min(−p_d, p_c)`.
   This makes at most (number of nonzero positions − 1) transfers. Optimal is NP-hard; nothing promises better.
6. **Pairs shown on screen:** for each unordered pair {u, v} with a planned route (steps 4–5) or any entry:
   - `target(u→v) = net_pre(u→v) + R(u→v) − R(v→u)`;
   - `paid(u→v) = net_all(u→v)`;
   - orient the pair so that target ≥ 0;
   - drop the pair if target = 0 and paid = 0;
   - `remaining = target − paid`. Positive means u pays v; negative means v pays u back.
   - With `paid > 0`: `mark` = contract P's mark and `difference = differenceFor(target, paid)` (contract D, `SETTLE_DIFF_IGNORE_CENTS`, unchanged).
   - With `paid ≤ 0`: no mark, and the route is `remaining` (it includes money v sent u earlier).
   - `outside` routes are listed separately, as today.
7. **Provenance** (for copy, A1.5):
   - for each person: `heldFor` = pre money they received on pairs where they aren't a current payer and which is now passed on;
   - for each sender: `passedOnBy`.
   Both are derived data, never stored.

**Output:** `{ key, pairs: Pair[], outside: Outside[], provenance }`, where `Pair = { fromId, toId, targetCents, paidCents, remainingCents, mark, difference }`. Pairs are ordered by `fromId`, then `toId` (S5's ordering rule); outside routes come after.

**Properties** (Task 2b; a seeded **simulation**, not just random inputs; ≥ 2,000 runs). Each run starts from a random bill (2–8 people, 1–4 payers, shares including 0 and negative), then applies 1–12 random steps:
- a bill change: new shares or payers, so a new key;
- a payment the UI allows on the current plan (pay a remaining pair, in full or in part), recorded with the current key;
- a pay-back of a `back` difference;
- an undo or not-received of a mark (A1.3);
- a raw pre-key payment to a current payer.

After every step:
- **Zeroing:** for every u, `p_all_u + Σ remaining out − Σ remaining in` (pairs and outside routes, exact, no tolerance) = 0.
- **Stability:** after a payment step, every pair other than the one paid is identical to before (deep-equal).
- **Single payer = today:** when there's one payer and every entry involves the current payer, the shown pairs equal today's `settlePlan` people (via `legacyMarksToPairs`, S1), and the result is the same whether those entries are pre or post (partition independence).
- **Deterministic:** permuting participants, payers and entries gives the same output.
- **Route bound:** routes planned in steps 4–5 ≤ nonzero positions − 1.
- Every pair with `remaining > 0` beyond tolerance has `toId` ∈ current payers.

**The suite must fail at least once** each:
- with step 1 treating every entry as pre (stability breaks);
- with step 4 removed (single-payer back cases break);
- with a 1¢ error injected into step 6.

The report says so (lesson 2026-11-26).

### Contract O, redefined (Task 6; Home, D10)
`balanceFor(plan, userId) → { owesCents, owedCents }`:
- **owes** = Σ `remaining` over pairs `from = user` where `remaining > 0` (a marked pair within tolerance counts 0), plus Σ `|remaining|` over pairs `to = user` where `remaining < 0` (a back the user owes).
- **owed** = the mirror image.
- `outside` routes never count (GV-4).
- On one-person plans from today's code path it equals the baseline in criterion A-25 (S2).
