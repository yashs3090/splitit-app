# Before production

Things to settle before SplitIt goes to real users (App Store, Play Store, a public web URL). Add an item here whenever a decision is "fine for dev, needs revisiting for prod". Tick items off with a date and a link to what was done.

Items marked *(unverified)* come from memory or general knowledge; check the current official docs before acting on them.

## 1. Identity and names (hard or impossible to change later)
- [ ] **App name.** Check "SplitIt" is free to use on the App Store / Play Store and doesn't clash with an existing trademark. Several apps with similar names exist (see the plan's research section).
- [ ] **Domain name.** Pick and buy one (the plan assumed `splitit.app`; not owned yet). Needed for: invite links (`https://<domain>/b/<code>`), the web app, universal/app links, the privacy policy page, and Google OAuth's authorized domains.
- [ ] **Bundle identifier is permanent.** Dev builds use `com.yashs3090.splitit` (iOS `bundleIdentifier` and Android `package` in `app.json`). Once published to a store it can't change. Decide whether to keep it or switch to something domain-based (e.g. `app.<domain>`) **before the first store upload**.
- [ ] **URL scheme** `splitit://` is used for native deep links. Confirm no other popular app uses it; universal links (below) are the safer production path.
- [ ] **App icon and splash art are still Expo's template placeholders (added 2026-11-25, visual pass V17 / P7, decision VP-19).** `assets/images/icon.png`, `android-icon-foreground.png` (blue Expo chevron), `android-icon-background.png` (blue grid) and `splash-icon.png` came with the project template. The splash and adaptive-icon colors are now SplitIt teal (`app.json`), but the Android icon's template background image still covers its teal color. Commission or make the real icon and splash mark (brand decision), then remove `android.adaptiveIcon.backgroundImage` or replace it. Check the splash on a dev build in light and dark (iOS and Android), since `app.json` changes only show after a native rebuild.

## 2. Accounts and costs
- [ ] **Apple Developer Program** (~$99/yr). Free Apple ID builds expire after 7 days and can't go to the App Store or TestFlight.
- [ ] **Google Play Console** (one-time fee, ~$25 *(unverified)*), only when shipping Android.
- [ ] **Hosted Supabase project.** Free tier may pause inactive projects *(unverified; check current terms)*; Pro is ~$25/mo and adds daily backups.
- [ ] **Web hosting** for the Expo web export (Vercel/Netlify/etc.) plus HTTPS on the domain.
- [ ] **EAS Build/Submit** plan, if building in the cloud instead of on this Mac.

## 3. Sign-in (Google OAuth + Supabase Auth)
- [ ] **Sign in with Apple is probably required on iOS.** Apple's App Review guideline 4.8 asks apps that offer third-party sign-in (like Google) to also offer an equivalent privacy-focused option *(check the current guideline wording)*. ADR 0008 chose Google-only "for now"; `supabase/config.toml` and `supabase/.env.example` already have disabled Apple placeholders.
- [ ] **Google OAuth consent screen:** move from "Testing" to "In production" (testing mode only allows listed test users). Add app name, logo, support email, privacy policy URL, authorized domain. Google may require verification.
- [ ] **Test users vs publishing (added 2026-11-22, M1b/M2).** Two-account QA of sharing and claiming works today only because the second Google account was added by hand as a test user (spec step U1). Every friend in the friend-test deploy would need the same, and Google caps the number of test users *(unverified: check the current cap)*. Before friends outside that list can join a bill, decide whether to publish the consent screen. That decision belongs to the friend-test deploy slice (spec A1.1).
- [ ] **Production redirect URIs** in Google Cloud Console: `https://<project-ref>.supabase.co/auth/v1/callback` (the local `http://127.0.0.1:54321/...` one is dev-only). Consider a separate OAuth client for prod.
- [ ] **Supabase Auth URL config** (dashboard): `site_url` = the production web URL; redirect allow-list = production domain + app scheme. Remove `localhost` and `exp://` entries from production.
- [ ] **Secrets in the hosted dashboard**, not files: the Google client secret goes into Supabase dashboard → Auth → Providers. Never commit `supabase/.env`.
- [ ] **Remove the Google OAuth variables from the root `.env` (user action, open since M1a; reported for the third time 2026-11-24).** `npx expo-doctor` still lists `google_oauth_webclient1_client_id` and `google_oauth_webclient1_client_secret` there (names only; agents don't read `.env`). The root `.env` should hold only `EXPO_PUBLIC_*` values. They aren't bundled today because they lack the `EXPO_PUBLIC_` prefix, but a rename or a copy-paste could ship the secret. Delete both lines. If the secret was ever shared or committed, reset it in Google Cloud Console.
- [ ] **Check the Google button against Google's branding kit (added 2026-11-25, visual pass V3 / P5, decision VP-2).** `components/GoogleSignInButton.tsx` follows Google's light/dark themes, but three things differ from the guidelines: the label uses the system font (Google asks for Roboto Medium 14/20; we don't bundle Roboto), the button is 44 pt tall (Google's is 40; ours meets the touch-target rule), and the G is drawn from Google's published path data rather than the downloaded asset. Before launch, compare it side by side with the official kit on iOS, Android and web, and decide whether to bundle Roboto (`expo-font`) or ship the official asset.

## 4. Database and security
- [ ] **Assume the API is public (added 2026-11-24).** The project URL and anon key ship in every copy of the app, and anyone can sign in with Google, so anyone can call the Data API directly and do everything their grants, RLS and functions allow, without the app. Only what the **database** refuses is actually prevented. Things the database currently *allows* that the screens don't offer, all affecting only the caller, are accepted risks: direct claim writes (PI-R-3, can deadlock against a host's save), "I paid" with nothing owed (PI-M-1), and marks of any amount from $0.01 to $999,999.99 (ADR 0015). *(Updated 2026-11-25, settle-early slice: K6, marking paid on an all-$0 bill, is removed from this list because the database now refuses it with `22023 all_zero` ([ADR 0021](learning/decisions/0021-settling-early-and-paying-differences.md)). Added: `settle_difference` lets a person raise their own mark to any amount up to $999,999.99, and lets the payer lower other people's marks down to clearing them ("I paid you back"). Both are self-reported and logged in Activity with who did it, and the second is weaker than `unmark_paid`, which the payer already has. See also the R8 item below.)* Before launch, re-review each one under that assumption, and add rate limiting (below). Explained in `docs/learning/concepts/row-level-security.md`, "The app is not the only client".
- [ ] **Apply migrations to the hosted project** (`npx supabase link`, then `npx supabase db push`), never by hand-editing in the dashboard.
- [ ] **All pgTAP tests pass** (`npm run db:test`) against the hosted database too. (Local: first real run passed 45/45 on 2026-11-20.)
- [ ] **Run Supabase's security and performance advisors** on the hosted project and fix findings.
- [ ] **Every table has RLS + explicit grants** (`revoke all ... from anon, authenticated, public`, then minimal grants). Re-audit before launch.
- [ ] **Abuse and rate limiting.** With no custom backend (ADR 0010), there's no server-side rate limit on things like bill creation or join-code guessing. Decide whether RLS + Supabase's built-in limits are enough, or whether we need an Edge Function. This is a "backend needed?" decision for the user.
  - *Update 2026-11-22 (M1b/M2):* what's exposed now is `create_bill`, `join_bill`, `set_claim`, `set_item_split`, `update_bill`, `rotate_join_code` and `set_extras_split` ([ADR 0013](learning/decisions/0013-writes-through-database-functions.md)). **Guessing codes isn't the risk**: they're 80 random bits, and wrong and malformed codes get the same error ([database functions](learning/concepts/database-functions.md)). **Spam is the risk.** A signed-in user (or a script holding their token) could create thousands of bills, join every bill they have a link to, toggle claims in a loop, or flood a bill's Activity log. Each claim toggle also sends a Realtime message to every phone on that bill.
  - Today the only limits are the 500-row cap per bill (`private.validate_bill_rows`), parts 1–20, and whatever Supabase's platform enforces *(unverified: check the hosted project's API and Realtime limits and the free-tier Realtime message and connection quotas)*.
  - Not limited at all: bills per user, participants per bill, and Activity events per bill. Consider a participant cap and a per-user bill cap inside the functions (no backend needed), and decide whether anything needs an Edge Function.
  - *Update 2026-11-24 (M3):* add `set_payer`, `mark_paid` and `unmark_paid` to the list. A script that marks and undoes in a loop writes an Activity event and sends a Realtime hint to every phone on the bill each time. (A repeated `mark_paid` with no undo in between is a no-op and sends nothing.)
  - *Update 2026-11-24 (People):* add `add_participant`, `remove_participant` and `leave_bill`. `add_participant` has no rate limit and there's still no cap on participants per bill, so a host could add every linked person to many bills, or add and remove the same person in a loop (each step writes an Activity event and sends a Realtime hint). A participants-per-bill cap inside `add_participant` and `join_bill` needs no backend.
  - *Update 2026-11-25 (settle early):* add `settle_difference`. A person can raise their own mark again and again, and the payer can lower and the person raise in turns; each step writes an Activity event (`paid_difference` / `paid_back`) and sends a Realtime hint to every phone on the bill. (An identical retry is a no-op and sends nothing.)

- [ ] **Home shows at most 20 bills (added 2026-11-24, starting value, decision BM-12).** `my_bills()` returns 20 rows, the same limit Home had before. The limit lives only in that function. Bills are ordered by when you joined or were added, newest first, so a bill you were just added to always shows, even if it's old. But once someone is on more than 20 bills, the older ones can't be reached from Home at all: there's no "Show more" or search yet. Add paging (or raise the limit) before real users pile up bills. - [ ] **The payer-change check compares a count, not names (added 2026-11-24, M3 review R5, decision M3-R-2).** `set_payer` compares the number of "I paid" marks with the count the host's confirm showed. If one mark is undone and a different one is added before the host confirms, the count still matches, so the change goes through and clears a mark the confirm never named. Example: the confirm says "clears 1 mark" (Sam's); Sam undoes, Dee marks; Hana confirms and Dee's mark is cleared. It's rare, the person can mark again, and it shows in Activity. The full fix is to pass the expected marked user ids instead of a count, which is a contract change (`set_payer`, `lib/bills.ts`, the Settle screen). Decide before launch ([stale-state checks](learning/concepts/stale-state-checks.md)).
- [ ] **"I paid" is an honor system (added 2026-11-24, M3).** Marks are self-reported, and `settled_cents` comes from the phone; the database checks only that it's a whole number from 1 to 99,999,999 cents. Nothing confirms a payment happened. Say so in the app's help or FAQ if friends rely on it. `unmark_paid` also has no stale-state check (decision M3-11): an Undo racing a re-mark can clear the new mark (the person can mark again).
  - *Update 2026-11-25 (settle early, [ADR 0021](learning/decisions/0021-settling-early-and-paying-differences.md)):* differences are self-reported too. `settle_difference` records "I paid $1.10 more" or "I paid you back $1.10" as stated; it can't check Venmo or the share. A mark now means the **net** amount settled, and a pay-back to $0 clears it.
- [ ] **A real double payment of a difference isn't flagged (added 2026-11-25, settle early, decision SE-ENG-3).** `settle_difference` treats a call whose result is already stored as a successful retry: no error, no second event. That's so a retry after a lost response doesn't say "Your 'I paid' just changed" for a write that worked. The cost: if Sam really pays "$1.10 more" from two phones at once, both raising 1510 → 1620, it's recorded once, and the extra $1.10 is invisible in the app. Decide whether that matters with real users.
- [ ] **No notice when a payer's Undo clears a mark whose share is now $0 or less (added 2026-11-25, decision SE-ENG-2, option A, chosen by the user).** After a pay-back to $0 the mark is cleared, and the Settle screen deliberately shows no "Your 'I paid' was undone" notice when the person's new share is ≤ $0 (it would be wrong after a real pay-back). The same rule also hides it when the payer used **Undo** instead of "I paid it back" on such a mark. Activity still shows "… undid …'s 'I paid'". Revisit if people miss pay-backs or undos.
- [ ] **1¢ differences are never asked for (added 2026-11-25, decision SE-11, starting value; money: waiting for the user's review).** `SETTLE_DIFF_IGNORE_CENTS = 1` in `lib/settle.ts` hides differences of ±1¢, because rounding alone can move an early share by 1¢. So a payer can end up 1¢ short or over per person. One constant; set it to 0 to show every cent ([money and rounding](learning/concepts/money-and-rounding.md)).
- [ ] **The Venmo username rule is partly unverified (added 2026-11-24).** The rule is `^[A-Za-z0-9_-]{5,30}$`, stored without `@`, in both `lib/venmo.ts` and the `profiles_venmo_username_format` check ([ADR 0007 note](learning/decisions/0007-payment-deep-links.md)). The length and the `-`/`_` symbols come from Venmo's help page. These parts are guesses *(unverified)*:
  - **ASCII letters only.** Venmo doesn't say whether accented letters (`josé1`) are allowed; we reject them.
  - **No first-character rule.** We allow handles that start with a digit or are all digits (`12345`).
  - **Case.** We store the case exactly as typed and never compare without case. We don't know whether Venmo treats `Jane-Doe` and `jane-doe` as the same account.

  Before launch, re-check https://help.venmo.com/cs/articles/check-or-edit-your-username-vhel208. If the rule is wrong, change `lib/venmo.ts` and the check constraint **together**, with the same boundary cases in both test files (spec D2). Until then, a real user whose handle the rule rejects can't save it.

- [ ] **Leak check** on the production web build: `grep -rE "service_role|sb_secret_" dist/` prints nothing. Only the anon/publishable key ships in the app.

- [x] **Direct claim writes can still deadlock (added 2026-11-24, People review R1 follow-up, decision PI-R-3). Accepted by the user 2026-11-24: we assume nobody writes claims directly through the API; the worst case is one failed save that the user retries. - [ ] **`settle_difference` token is a value, not a version (added 2026-11-25, settle-early review R8).** The stale-state token `p_expected_cents` compares amounts. The app's own retry rebuilds the action from fresh data, so this needs a direct API caller or a contrived sequence (accepted caller-side risk, see "Assume the API is public"). Full fix: a per-row version counter as the token.

## 8. Dev-only things to remove or change
- [ ] **No live "added you" card while Home is open (added 2026-11-24, decision BM-11).** Home reloads its list when it comes into view and when the app (or, on web, the browser tab) comes back to the front. It doesn't listen live. So if someone is looking at Home when they're added to a bill, the card doesn't appear until they open something and come back, switch away and back, or reopen the app ([realtime](learning/concepts/realtime.md#home-doesnt-use-realtime-2026-11-24-decision-bm-11)). There's also no push notification, by the user's choice (in-app only). If friend testers miss adds, upgrade before launch: a private per-user Realtime topic (`user:<id>`) with its own `realtime.messages` policy, plus a hint sent from `add_participant`. Push notifications would need APNs/FCM setup and a paid Apple Developer account (§2).
- [ ] Local-only redirect URLs (`localhost:8081`, `exp://**`) out of the production Auth config.
- [ ] Any dev-only buttons (e.g. a planned "Copy recognized text" debug button) hidden behind `__DEV__`.
- [ ] Placeholder OAuth values (`replace-me`) never used outside local dev.
