# Before production

Things to settle before SplitIt goes to real users (App Store, Play Store, a public web URL). Add an item here whenever a decision is "fine for dev, needs revisiting for prod". Tick items off with a date and a link to what was done.

Items marked *(unverified)* come from memory or general knowledge; check the current official docs before acting on them.

## 1. Identity and names (hard or impossible to change later)
- [ ] **App name.** Check "SplitIt" is free to use on the App Store / Play Store and doesn't clash with an existing trademark. Several apps with similar names exist (see the plan's research section).
- [ ] **Domain name.** Pick and buy one (the plan assumed `splitit.app`; not owned yet). Needed for: invite links (`https://<domain>/b/<code>`), the web app, universal/app links, the privacy policy page, and Google OAuth's authorized domains. **Universal/App Links are tied to the host (added 2026-11-26):** the app claims only the host of `EXPO_PUBLIC_WEB_URL` at build time (today `splitit-app-kappa.vercel.app`). Switching to a bought domain means a new app build and store release, both well-known files on the new domain, and keeping the old host's files up until old installs have updated ([app links guide](setup/app-links.md)). Pick the domain before the first store release if you can.
- [ ] **Bundle identifier is permanent.** Dev builds use `com.yashs3090.splitit` (iOS `bundleIdentifier` and Android `package` in `app.json`). Once published to a store it can't change. Decide whether to keep it or switch to something domain-based (e.g. `app.<domain>`) **before the first store upload**.
- [ ] **URL scheme** `splitit://` is used for native deep links. Confirm no other popular app uses it; universal links (below) are the safer production path.
- [ ] **App icon and splash art are still Expo's template placeholders (added 2026-11-25, visual pass V17 / P7, decision VP-19).** `assets/images/icon.png`, `android-icon-foreground.png` (blue Expo chevron), `android-icon-background.png` (blue grid) and `splash-icon.png` came with the project template. The splash and adaptive-icon colors are now SplitIt teal (`app.json`), but the Android icon's template background image still covers its teal color. Commission or make the real icon and splash mark (brand decision), then remove `android.adaptiveIcon.backgroundImage` or replace it. Check the splash on a dev build in light and dark (iOS and Android), since `app.json` changes only show after a native rebuild.
  - *Web home-screen icons too (added 2026-11-26, Home mobile refresh, decision HR-15, question Q1 still open).* `public/apple-touch-icon.png` (180×180), `public/icons/icon-192.png` and `public/icons/icon-512.png` are the same placeholder, resized. They're what "Add to Home Screen" and the web manifest show. Replace them in the same task as the native icon, keeping the file names and sizes. `__tests__/webTemplate.test.ts` fails if any is the wrong size or over 200 KB. If a plain resize of the real icon comes out over 200 KB, drop its alpha channel and recompress ([mobile web](learning/concepts/mobile-web.md#the-icons-are-placeholders)).
- [ ] **Username squatting and the reserved list (added 2026-11-28, [usernames spec](specs/2026-11-28-usernames.md), UN-5, Q1).** Handles are first come, first served. Before launch, review the starting reserved list (`RESERVED_USERNAMES` in `lib/username.ts` and the `profiles_username_reserved` constraint, which must stay identical). Also decide whether to block look-alikes by substring (e.g. `splitit_support`, `admin.team`), brand and staff names, and offensive words. Changing the list later doesn't touch handles already taken, so decide early.
- [x] **Username rename policy (added 2026-11-28, usernames spec, Q3). Resolved 2026-11-28 by the user (spec Amendments A2 and A3): no renames.** The username given at sign-up is provisional; the person picks once (`set_username`, which may keep the provisional name), and from then on it never changes. `username_locked_at` records the pick, and the `profiles_username_lock` trigger refuses any later change for every role (`42501 username_immutable`), in `20261128111928_username_lock.sql`. Venmo usernames stay editable (A2.8).
- [ ] **Should a deleted account's username be retired? (added 2026-11-28, usernames spec A2.7, open question for the user).** When an account is deleted, its profile row goes (cascade), so its username is free for the next person who signs up or picks it. Someone new could then take a handle that friends recognise. The alternative is to retire handles forever: a small `retired_usernames` table that `private.assign_username` and `set_username` check. Not built; decide before launch, because handles freed before the table exists can't be retired afterwards.
- [ ] **Can the username pick be skipped? (added 2026-11-28, usernames spec A3.6 / UN-18, open).** The pick step's default is required, with "Keep @name" as the one-tap choice. Until the screen ships, every account keeps an unlocked, provisional username, so the first pick can still change it.
- [ ] **Username search: add a narrow lookup, don't open the table (added 2026-11-28, user agreed in chat).** Today a username is readable only by the owner and people who share a bill or group (display_name's rule, tested in pgTAP). Search needs strangers to find you, so it will loosen this, but only through one search function, never by widening `profiles`' row policy. The function should: match the exact handle only (no prefix or "contains" search, no listing); return only the username, display name and the id needed to invite (never `venmo_username`); be `security definer` with `search_path = ''`, executable by `authenticated` only; and be rate-limited per user (see the probing note in §4). Browsing `profiles` stays limited to people you share something with. Record it as an amendment to [ADR 0026](learning/decisions/0026-usernames.md) when search is built.

## 4. Database and security
- [ ] **Assume the API is public (added 2026-11-24).** The project URL and anon key ship in every copy of the app, and anyone can sign in with Google, so anyone can call the Data API directly and do everything their grants, RLS and functions allow, without the app. Only what the **database** refuses is actually prevented. Things the database currently *allows* that the screens don't offer, all affecting only the caller, are accepted risks: direct claim writes (PI-R-3, can deadlock against a host's save), "I paid" with nothing owed (PI-M-1), and marks of any amount from $0.01 to $999,999.99 (ADR 0015). *(Updated 2026-11-25, settle-early slice: K6, marking paid on an all-$0 bill, is removed from this list because the database now refuses it with `22023 all_zero` ([ADR 0021](learning/decisions/0021-settling-early-and-paying-differences.md)). Added: `settle_difference` lets a person raise their own mark to any amount up to $999,999.99, and lets the payer lower other people's marks down to clearing them ("I paid you back"). Both are self-reported and logged in Activity with who did it, and the second is weaker than `unmark_paid`, which the payer already has. See also the R8 item below.)* Before launch, re-review each one under that assumption, and add rate limiting (below). Explained in `docs/learning/concepts/row-level-security.md`, "The app is not the only client".
- [ ] **The privacy of feed amounts is display-only (added 2026-11-28, tab bar and Activity, Task 12; spec risk R1, FEED-9, [ADR 0025](learning/decisions/0025-tab-bar-and-activity.md) §5).** The Activity tab shows an amount only for your own money ("Sam marked $18.20 paid to you") and never what two other people paid each other. That rule lives only in the app (`classifyFeedEvent` in `lib/feedRules.ts`). RLS lets every participant read every `bill_events` row on their bills, amounts included (`bill_events_select_participant`; members read every `group_events` row the same way), and the per-bill Activity screen already shows them. So anyone on a bill, with a script and their own login, can read what Sam paid Maya. Before real users, decide whether that's acceptable. If those amounts must be private, the fix is in the database (a narrower policy, or a definer read function that leaves them out), not in the app ([row-level security](learning/concepts/row-level-security.md), "The Activity feed: privacy that is only a display rule").
- [ ] **Activity badge and unread dots are device-local (added 2026-11-28, tab bar and Activity, Task 2; FEED-28, FEED-29, FEED-30).** `lib/feedSeen.ts` stores when you last opened Activity, each bill and each group under `splitit.feedSeen.<userId>` in `lib/storage` (SecureStore on native, localStorage on web), not in the database (user, U11). So the badges are per device: a second phone, a reinstall or cleared browser data shows the last 14 days as unread once (`FEED_FIRST_RUN_DAYS`, a starting value), and anything older than 14 days never counts. Decide with real users whether that is acceptable or whether seen state should move to the server.
- [ ] **Seen times come from the phone's clock, event times from the server's (added 2026-11-28, tab bar and Activity review R3).** `lib/feedSeen.ts` stores when you opened Activity, a bill or a group using the phone's clock (`Date.now()`), and `isFeedItemSeen` compares that with each event's `created_at`, which the database sets. If the phone's clock is behind the server, events written in that gap stay "unread" after you've looked at them; if it's ahead, events written in that gap are marked seen before you could have seen them, so they never light the badge. Activity's own stamp (`activitySeenStamp` in `lib/useActivityFeed.ts`) uses the focus start time, or the newest loaded line's `created_at` if that's later, so everything Activity showed you counts as seen whatever the clock says, and nothing written while the page loaded is swallowed. Bill and group opens still use the phone's clock alone. A clock off by a few seconds doesn't matter; a phone set minutes or hours wrong (manual time, travel) would. If testers report badges that won't clear or events that never show as new, stamp bill and group opens with the newest `created_at` the screen loaded too, or read the server's time once per session and keep the offset.
- [ ] **Feed and badge read cost, and id-chunk URL length, are unmeasured on hosted data (added 2026-11-28, Task 2; Risk R2).** `lib/activityFeed.ts` reads `bill_events` / `group_events` across all your bills and groups in chunks of `FEED_ID_CHUNK` = 100 ids per `.in()` filter, each with `count: 'exact'`, on every Activity page and every badge refresh (tab change, foreground, after each seen write). `group_events` has no `created_at` index (only `(group_id, seq desc)`), and the exact counts scan every matching row. Measure on the hosted project with a heavy account, check that a 100-uuid URL (about 3.7 KB of filter) stays under the gateway's URL limit, and lower the chunk size or drop the counts for short pages if needed.

- [ ] **In-app account deletion.** Apple requires apps with account creation to let users delete their account in the app *(guideline 5.1.1(v))*.
  - **Possible deadlock when deleting a payer's account (added 2026-11-24, M3 review R9).** The payer-deletion trigger on `bill_participants` (`supabase/migrations/20261124081411_settle_payer.sql:94-108`) locks the participant row and then the bill. `unmark_paid` (`20261124081412_settle_marks.sql:134-150`) locks the bill and then the participant row. A deletion at the same moment as an undo of that payer's mark could deadlock, and Postgres would abort one of them. When account deletion is built, take the locks in the same order, or retry on `40P01`.
    - *Also `set_not_part` (added 2026-11-27, group claim status, `supabase/migrations/20261127150000_bill_not_part.sql`).* It takes the bill `FOR KEY SHARE` first, then waits for the caller's own participant row (`FOR UPDATE`). The payer-deletion trigger holds that participant row (it's being deleted) and then wants the bill `FOR UPDATE`, which conflicts with the key-share lock. So if a group bill's payer (not its host) deletes their account at the same moment as their own "I wasn't part of this" or Undo on that bill, one of the two could be aborted with `40P01`. Very unlikely, but include it in the same lock-order fix. The migration header lists every lock it takes.

  - Decide whether that's the behavior we want. Deleting a guest's account silently changes other people's bills: their claims vanish and shares are recalculated. That matters once M3 settling exists.
  - *Venmo username (2026-11-24):* it's a column on `profiles`, so deleting the account deletes it too. Nothing else stores it.
  - *Deleting the payer's account (2026-11-24, M3):* the bill goes back to the host, every "I paid" mark on it is cleared, and Activity logs one payer change with no actor ([ADR 0015](learning/decisions/0015-settling-one-payer-self-reported-marks.md), decision M3-9). People who had already paid the deleted person keep no record of it on the bill. Decide whether that's right once account deletion is built (the alternative is blocking deletion while you're someone's payer).
  - *Group members can't delete their account (2026-11-27, Groups MVP, decisions GR-26 and S8; [ADR 0022](learning/decisions/0022-groups.md)):* `group_members.user_id` references `profiles` with `on delete restrict`, and someone with group history (bills, expenses or payments) can't leave the group.
